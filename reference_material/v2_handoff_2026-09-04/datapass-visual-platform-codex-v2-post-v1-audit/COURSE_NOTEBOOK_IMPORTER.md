# Course and notebook importer

## Purpose

The first real learning consumers have valuable `.ipynb` source material. The website should **not** look like a raw Jupyter notebook. V2 needs a deterministic build-time importer that turns notebooks into structured course content while preserving provenance.

## Import pipeline

```text
.ipynb
  |
  +-- metadata/provenance
  +-- markdown cells
  +-- code cells
  +-- saved outputs
  +-- media references
  |
  v
NotebookSpec
  |
  v
LessonSpec / CourseSpec
  |
  v
Fluent Learning Workbench
```

No kernel is required.

## Required importer behavior

- parse notebook JSON at build/import time;
- preserve deterministic cell IDs;
- preserve original source file and SHA-256;
- normalize Markdown safely;
- recognize code language from metadata/content;
- preserve saved text/table/image outputs as **reference/source outputs**;
- copy referenced local media deterministically;
- strip or sanitize unsafe raw HTML/script content;
- report unsupported MIME types instead of silently injecting them;
- emit deterministic JSON so reimporting unchanged content produces no diff;
- provide import warnings with source file + cell index/ID;
- never execute notebook code as part of import.

## Learning transformation

Do not render every source cell with full Jupyter chrome.

The consumer should be able to transform imported content into:

- lesson title;
- objective/key points;
- prose sections;
- compact code examples;
- editable exercise cells;
- expected/reference output;
- ConceptMotion Figure blocks;
- hints;
- solution/reveal/diff;
- QCM/review;
- source/download actions.

## Deepnote SQL extraction

The supplied SQL course notebooks contain code cells generated by Deepnote, commonly shaped like:

```python
_dntk.execute_sql(
  'SELECT ...',
  'SQL_DEEPNOTE_DATAFRAME_SQL',
  ...
)
```

V2 should provide a **conservative build-time extractor** that recognizes this known wrapper and exposes the embedded SQL string as the learner-facing code.

Requirements:

- preserve the original wrapper in provenance/debug metadata;
- extract only when the pattern is unambiguous;
- fallback to the original code cell if extraction fails;
- never use `eval`;
- add tests covering multiline strings, comments, apostrophes and incomplete exercise placeholders;
- keep referenced CSV paths for possible future DuckDB/browser use.

This makes the SQL course feel native rather than showing irrelevant Deepnote plumbing.

## Exercise recognition

The importer may use explicit mappings/configuration to mark cells as:

- example;
- exercise starter;
- hint;
- solution/reference;
- expected output.

Do not rely on fragile AI inference in the build step. Deterministic mapping files are preferred.

## PySpark policy

For PySpark notebooks:

```text
source notebook
     |
     v
read-only rich lesson
  + code
  + saved output
  + ConceptMotion explanation
  + quiz
  + external runtime launcher
```

No Spark execution is required or claimed.

## Browser execution later

Keep an `ExecutionAdapter` interface possible, but do not make it part of the pure NotebookSpec.

Possible future adapters:

- DuckDB-WASM for compatible SQL;
- Pyodide for compatible Python;
- external Colab;
- external Databricks;
- Voila/Mercury;
- later Jupyter gateway.

V2 required UI must remain fully useful when `execution = none`.
